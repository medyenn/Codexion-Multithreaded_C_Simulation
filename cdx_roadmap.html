Codexion is a multithreaded C simulation: coders competing over shared USB "dongles" under strict deadlines, arbitrated by fifo or edf scheduling. How this course is built, and how to use it.

This document has three jobs, in order:

  2. Dissect the subject line by line, so every rule maps to something you already understand from step 1.

PART I — FOUNDATIONS
01

Concurrency Foundations

Processes vs. threads, and why the OS lies to you about order.

Process vs. thread

A process is an isolated program: its own memory space, its own everything. A thread is a unit of execution inside a process. Multiple threads in the same process share the process's heap, global data, and open files — but each thread keeps its own private stack, its own registers, and its own program counter (where it currently is in the code).

SHARED between threads

  • Heap (malloc'd memory)
  • Global / static variables
  • Open file descriptors

PRIVATE to each thread

  • Its own stack (local variables)
  • Its own registers / program counter
  • The argument passed to it at creation

This is the entire reason threads are useful here: a coder and the simulation's shared state (dongles, logs, timers) must be the same memory, visible to every coder thread and the monitor thread simultaneously — which is exactly what "shared" memory gives you, and exactly what makes it dangerous.

Concurrency vs. parallelism

Concurrency is a property of the program's structure: multiple logical tasks make progress over overlapping time windows. Parallelism is a property of the hardware: tasks literally execute at the same instant on different cores. Codexion must be correct under concurrency regardless of whether it happens to run in parallel — your code must never assume a particular number of cores, or that any two operations happen "at the same time" in a way you can rely on.

Interleaving: the only assumption you're allowed to make is none

The OS scheduler may pause and resume any thread at almost any instruction boundary, in any order, for any duration. A program is correct only if it behaves correctly under every possible interleaving — not just the one you happened to observe while testing. "It worked when I ran it ten times" proves nothing about interleaving #11.

Why the subject bans global variables Global variables are the easiest way to accidentally create unsynchronized shared state. Forbidding them forces every piece of shared data to travel explicitly through function parameters (pointers to one shared struct), which makes ownership and access visible — you can grep for every place a dongle is touched instead of hoping you remembered them all.
02

Races, Deadlock, Starvation

The three ways concurrent code fails — and the two properties that prove it doesn't.

Critical sections & mutual exclusion

A critical section is any piece of code that reads or writes shared state in a way that isn't safe if another thread does the same thing simultaneously. Mutual exclusion is the guarantee that at most one thread executes a given critical section at a time.

Race conditions

A race condition occurs when the correctness of a result depends on the relative timing of unsynchronized accesses to shared memory. In Codexion: two coders reading and writing "is this dongle available?" without a lock could both conclude it's free and both grab it — a duplicated dongle. The test_codexion.sh script literally has a check for this (the "two-dongle rule").

Deadlock — Coffman's four conditions

A deadlock is a cycle of threads each waiting on a resource held by the next. It requires all four of these to hold simultaneously — break any one, and deadlock becomes impossible:

ConditionMeaningIn Codexion terms
Mutual exclusionA resource can be held by only one owner at a time.A dongle is either free or held by exactly one coder.
Hold and waitA thread holds one resource while waiting for another.A coder grabs its left dongle, then waits for the right one.
No preemptionA resource can't be forcibly taken away.You can't yank a dongle out of someone's hand.
Circular waitA cycle of threads each waiting for the next.Every coder holds their left dongle and waits for their right — a full circle, all waiting forever.

This exact circular scenario is the textbook Dining Philosophers deadlock — you'll design around it explicitly in Phase 09.

Starvation

Even a deadlock-free system can let one thread wait forever if the arbitration policy is unfair. This is why the subject mandates a deterministic scheduler (fifo or edf) with a required tie-break rule: an arbitrary or biased grant order could starve one coder indefinitely even though no deadlock ever occurs.

Safety vs. liveness

SAFETY

"Nothing bad ever happens." No dongle duplication, no data race, no interleaved log lines.

LIVENESS

"Something good eventually happens." No coder waits forever; the simulation eventually stops.

The grading rubric checks both: memory/race tools (valgrind, helgrind) verify safety; the repeated stress runs in stress_test.sh verify liveness.

03

POSIX Threads in C

How C actually represents "a thread," and its lifecycle.

The mental model

pthread_t is an opaque handle. Creating a thread means: give the OS a function pointer and one void* argument; it starts running that function concurrently with everything else, sharing the process's heap and globals but owning its own stack.

Lifecycle

StageWhat happens
Createpthread_create spawns the thread; it begins executing immediately, concurrently with the caller.
RunThe thread executes its function body, reading/writing shared memory through synchronization primitives.
Joinpthread_join blocks the caller until the target thread finishes, and reclaims its resources.
Design implication The allowed function list has pthread_join but no detach function. That means: every coder thread and the monitor thread must be joined by main before the program exits — and it's only after every join succeeds that it is safe to destroy mutexes/condition variables and free memory. Join order becomes part of your cleanup design.

Passing data to a thread

pthread_create only accepts a single void*. To give a thread several pieces of information (its coder id, and a pointer to the shared environment), you pass a pointer to a small per-thread struct — never a raw integer cast into a pointer, which produces warnings under -Wall -Wextra -Werror on many platforms and is simply bad practice.

Compilation

On Linux, POSIX threads require the -pthread flag at both compile and link stages — not just -lpthread. This is exactly why the subject's required flags are -Wall -Wextra -Werror -pthread; your Makefile's CFLAGS must carry it.

Always check return values

Every pthread_* function returns 0 on success or a nonzero error code directly (not via errno). A silently failed pthread_create for coder #7 out of 50 would leave your simulation running with a phantom coder — check every call.

04

Synchronization Primitives

Mutexes stop collisions. Condition variables stop wasted spinning.

The mutex

A mutex is a binary lock: lock() blocks until no other thread holds it, then takes ownership; unlock() releases it. Rules that matter here:

  • The thread that locks a mutex must be the one that unlocks it.
  • Every code path out of a locked section — including early returns and error paths — must unlock before leaving. A "forgot to unlock on the error branch" bug is a silent, hard-to-reproduce deadlock.
  • A mutex only prevents simultaneous access. It cannot make a thread "wait efficiently for a condition to become true" — busy-checking a flag while holding the lock wastes CPU and can even deadlock if only the lock-holder itself could ever change that flag.

The condition variable

A condition variable (always paired with a mutex) lets a thread sleep until another thread says "something changed," without spinning. pthread_cond_wait atomically (1) unlocks the mutex and (2) sleeps — then, once woken, re-locks the mutex before returning. That atomicity is the entire point: there's no gap where another thread could change the state between "I checked" and "I started waiting."

The predicate loop is not optional Always wait like this — conceptually — while (!condition_is_true) wait();, never with a plain if. Two independent reasons: (1) spurious wakeups — POSIX allows a thread to wake up from a condition wait with no signal having occurred at all; (2) even after a real signal, another thread might race in and consume the state first. Re-checking the actual predicate after waking, under the lock, is the only safe pattern.

Signal vs. broadcast

CallWakesUse when
pthread_cond_signalAt most one waiterYou know exactly one waiter could possibly proceed.
pthread_cond_broadcastEvery waiterMany waiters must re-check state (simpler to reason about, at a small extra wake-up cost).

Given this project's goal of maximal simplicity, broadcast + re-check under the priority queue's own decision is the easier pattern to prove correct: every waiter wakes, checks "is it actually my turn according to the scheduler," and goes back to sleep if not. It costs a few extra wake-ups; it costs nothing in correctness or clarity.

pthread_cond_timedwait: the monitor's secret weapon

This variant waits until either it's signaled, or an absolute deadline (a struct timespec in absolute — not relative — time) passes on its own. This single primitive is what makes precise burnout detection possible without polling in a tight loop: the monitor thread can sleep exactly until the nearest deadline and wake up precisely then.

Destruction

Every initialized mutex and condition variable must be destroyed exactly once, and only after no thread can possibly touch it again — i.e., after every thread that could use it has been joined. Destroying too early is undefined behavior; never destroying it is a (minor, but real) resource leak.

atoi can't validate anything atoi("abc") and atoi("0") both return 0 — indistinguishably. The subject requires rejecting negative numbers and non-integers. This lines up exactly with the subject's own hint that gettimeofday() "is acceptable and recommended for simplicity" here.

Time in Codexion

One baseline, one conversion function, one absolute-deadline formula.

The baseline

Capture a single timestamp, t0, once — immediately after argument parsing, before any thread is created. Every log line's timestamp and every deadline computation is expressed relative to t0.

elapsed_ms(now)

(now.tv_sec - t0.tv_sec) * 1000 + (now.tv_usec - t0.tv_usec) / 1000

Two time representations, two purposes

RELATIVE ms since t0

What every log line prints, and how you reason about "time_to_burnout ms since the last compile started."

ABSOLUTE struct timespec

t0 + deadline_ms, expressed as seconds + nanoseconds — the only format pthread_cond_timedwait accepts.

The 10 ms tolerance

The subject allows the burnout log to appear up to 10 ms after the actual burnout instant. That's an acknowledgment of OS scheduling jitter — not a license to poll every 10 ms in a busy loop. Compute the exact deadline, hand it to pthread_cond_timedwait, and let the kernel wake you precisely at (or extremely close to) that instant.

07

Scheduling & Heaps

Why EDF is provably fair, and how to build the only data structure the subject truly demands.

FIFO

Serve requests strictly in arrival order. Simple to implement, trivially fair by construction — as long as every request is eventually served, no one starves.

EDF — Earliest Deadline First

Serve whoever's deadline = last_compile_start + time_to_burnout is soonest. This is a classical real-time scheduling result: for a single shared resource among tasks with hard deadlines, EDF is the optimal online policy — if a feasible schedule exists at all, EDF will find it. That's precisely the subject's own liveness clause: "no coder should starve under edf, provided the parameters are feasible." EDF's guarantee is conditional on feasibility, not magic — if your timing parameters are simply impossible (as in the deliberate burnout benchmark cases), even a perfect scheduler can't save every coder.

Why a tie-break is mandatory, not decorative Two deadlines could — rarely, but possibly — be numerically equal. Comparing only by a single real-number key makes the ordering ambiguous in that case. A deterministic secondary key (e.g. coder id or a monotonically increasing arrival sequence number) removes the ambiguity entirely, which is what "fully deterministic EDF policy, even in edge cases" is asking for.

Binary heaps, from scratch

The subject explicitly forbids any standard-library priority queue, so the heap must be hand-written. A binary heap is a complete binary tree stored flat in an array:

  • For index i (0-based): parent is (i-1)/2, children are 2i+1 and 2i+2.
  • Insert: append at the end, then "sift up" — swap with the parent while smaller than it.
  • Extract-min: read the root, move the last element to the root, shrink the array, then "sift down" — swap with the smaller child while larger than it.
  • Both operations are O(log n) — irrelevant for a handful of coders, but it's the correct, standard structure regardless of scale.
One heap engine, not two Keep the heap itself completely generic: it only ever compares a numeric "key" per entry. At startup, based on the scheduler argument, decide what that key means — a monotonically increasing arrival counter for fifo, or the burnout deadline for edf. One heap implementation now serves both policies, and the FIFO→LIFO recode exercise mentioned in the grading sheet becomes a one-function change (flip the comparison), not a rewrite.

The Subject, Deconstructed

Every rule from the PDF, translated into an engineering requirement.

The eight arguments

#ArgumentMeaning
1number_of_codersCoder count — and dongle count (see below).
2time_to_burnout (ms)Deadline window since the start of the last compile, or since simulation start if none yet.
3time_to_compile (ms)Duration held with two dongles.
4time_to_debug (ms)Duration of the debug phase.
5time_to_refactor (ms)Duration of the refactor phase; immediately followed by a new dongle request.
6number_of_compiles_requiredSimulation stops once every coder has reached this many completed compiles.
7dongle_cooldown (ms)Minimum time a dongle sits idle after release before it can be taken again.
8schedulerExactly fifo or edf — reject anything else.

All eight are mandatory and must be validated: reject negative numbers, non-integer strings, and any scheduler value other than the two literal strings.

The circular table

Coders are numbered 1…N and seated in a circle: coder 1 sits next to coder N, and any coder N sits between N-1 and N+1. There is exactly one dongle per adjacent pair — which works out to exactly number_of_coders dongles total, each shared by two neighbors.

The n = 1 special case With a single coder, there is only one dongle on the table — "left" and "right" refer to the same physical dongle. Since compiling needs two distinct dongles held simultaneously, a lone coder can mathematically never compile and is guaranteed to burn out. This is exactly the first benchmark case in the grading rubric (./codexion 1 800 200 200 200 10 0 fifo) — your dongle-count and neighbor logic must produce this outcome naturally, not as a special-cased "if n == 1" hack.

Compiling / debugging / refactoring — mutually exclusive states

A coder is in exactly one of these three states at a time. The cycle is fixed: compile → debug → refactor → (immediately request dongles again) → compile → …

Burnout — the precise definition

"If a coder did not start compiling within time_to_burnout ms since the beginning of their last compile or the beginning of the simulation, they burn out."

The subtlety almost everyone misses The deadline resets at the moment compiling starts — not when it ends, and not when the coder requests dongles. This means the clock keeps running through debug, refactor, and any time spent waiting for dongles. A coder can absolutely burn out while sitting in the request queue, not only while idle.

Stop conditions

The simulation stops the instant either of these becomes true:

  • Any coder burns out (immediate, hard stop).
  • Every coder has completed at least number_of_compiles_required compiles.

Cooldown

Applies strictly after release: a dongle is unavailable for dongle_cooldown ms starting the moment its previous holder puts it down — not while it's being held.

Fair arbitration

fifo: strict arrival order. edf: earliest last_compile_start + time_to_burnout first, with a deterministic tie-break. The program must guarantee liveness under edf for feasible parameters, and a dedicated monitor thread must detect burnout to within 10 ms.

Log format — must match exactly

timestamp_in_ms X has taken a dongle
timestamp_in_ms X is compiling
timestamp_in_ms X is debugging
timestamp_in_ms X is refactoring
timestamp_in_ms X burned out

The test harness parses these lines with awk/grep — exact wording, exact spacing, one message per line, never interleaved with another line.

Build & submission rules

  • Binary named codexion; compiles with -Wall -Wextra -Werror -pthread, zero warnings.
  • Custom priority queue mandatory — no standard-library heap/priority queue.
  • Zero memory leaks; zero unexpected crashes (any crash → automatic 0).
  • No global variables, anywhere.
  • Makefile rules: NAME, all, clean, fclean, re — no unnecessary relinking.
  • libft is not authorized for this project.

README requirements

At the repository root, in English, first line italicized and exactly formatted as "This project has been created as part of the 42 curriculum by <login1>[, <login2>…]", plus these sections:

  • Description — purpose and overview.
  • Instructions — compile / install / run.
  • Resources — references used, and an honest account of how AI was used and for what.
  • Blocking cases handled — every concurrency issue you addressed (deadlock, starvation, cooldown, precise burnout, log serialization).
  • Thread synchronization mechanisms — the actual primitives you used and how they coordinate access to dongles, logging, and monitor state, with concrete examples of how races are prevented.

The recode exercise

The evaluation may ask for a small live modification — the grading sheet's own example is turning fifo into a lifo scheduler (most recent requester served first). If your scheduling decision truly lives in one isolated comparison function (see Phase 07's "one heap engine"), this becomes a five-minute, single-function edit instead of a scramble.

Philosophers in Disguise

Recognizing the classic problem underneath — and picking the simplest correct fix.

The mapping

Dining PhilosophersCodexion
PhilosopherCoder
ForkDongle
Needs both forks to eatNeeds both dongles to compile
Circular tableCircular seating, exactly as specified

This identity is exact. Every classic risk (and classic fix) applies directly.

Why the naive approach deadlocks

If every coder independently does "lock left dongle's mutex, then lock right dongle's mutex," and all N coders do this at once, every coder ends up holding its left dongle while waiting forever for its right — a perfect circular wait. This is Coffman's four conditions, satisfied simultaneously, by construction.

Classic textbook fixes (for context)

  • Resource ordering: odd-numbered coders pick left-then-right, even-numbered pick right-then-left — breaks circular wait by forcing at least one coder to eventually pick the "shared" dongle in an order that can't complete a cycle.
  • Arbiter / limited concurrency: only allow N−1 coders to attempt acquisition simultaneously — breaks hold-and-wait globally.
The simpler fix this project's spec actually points to Don't have coders lock two independent per-dongle mutexes at all. Instead, route every acquisition through one central arbiter — the priority queue/heap itself, guarded by a single mutex + condition variable. A coder submits one combined request for "my left and right dongle" as an atomic unit; the arbiter grants both together or neither. There is never a moment where a coder holds one dongle while waiting for the other — which means hold-and-wait, and therefore circular wait, and therefore deadlock, is structurally impossible. It also happens to be the simplest option: one lock to reason about, one queue, one grant function — exactly the "no over-engineering" outcome you're after.

This single decision is the architectural spine of the whole project: dongles are passive data (an availability flag + a last-release timestamp), not independently lockable objects that coders fight over directly. All the actual arbitration logic lives in one place.

10

Scope & Design Philosophy

Turning "simple, minimal, procedural" into concrete rules.

  • One shared struct owns everything. Parsed arguments, coder array, dongle array, the heap, the base timestamp, the logging mutex — all fields of one struct, passed everywhere by pointer. This is your entire answer to "no global variables."
  • One function, one responsibility. Aim for short, single-purpose functions — this isn't just a style preference, it's the Norm's own function-length rule (Phase 14).
  • No speculative abstraction. No generic "event system," no multiple heap types, no plugin architecture. One heap. One monitor. One logging function. The only justified indirection is the scheduler's compare rule, because the subject itself demands it be swappable (fifo/edf, and the recode exercise).
  • Errors are handled, never ignored, never fatal-by-accident. Every syscall, every pthread_* call, every malloc gets its return value checked and handled with a clean, symmetric teardown — because an unhandled failure path is exactly the kind of "unexpected exit" the subject scores as an automatic zero.
  • Prove it in isolation before wiring it together. The heap can be built and hand-tested with no threads at all. The logger can be smoke-tested with a trivial multi-thread program before it's used for real. Build bottom-up, verify each layer, then connect them.

Data Blueprint

Every struct's fields, described in prose — no code.

t_dongle

  • id — its position on the table.
  • is_available — whether it currently sits free.
  • last_release_ms — timestamp used to enforce the cooldown window.

No per-dongle mutex — arbitration is centralized (Phase 09), so a dongle is pure data, only ever touched while the one central lock is already held.

t_coder

  • id — 1…N.
  • left_dongle_id / right_dongle_id — its two circular neighbors.
  • compiles_done — progress toward number_of_compiles_required.
  • last_compile_start_ms — the value the burnout deadline is computed from.
  • state — an enum: waiting / compiling / debugging / refactoring.
  • a pointer back to the one shared environment struct.

t_request (a heap entry)

  • coder_id — who is asking.
  • key — either an arrival sequence number (fifo) or a deadline timestamp (edf), chosen once at startup.

t_heap

  • a dynamically-sized array of t_request, current size, and capacity.
  • a flag recording which comparison mode is active.
  • one mutex and one condition variable — this is the central arbiter.

t_env — the one shared struct

  • the parsed, validated arguments.
  • the array of coders, the array of dongles, the heap.
  • t0 — the simulation's base timestamp.
  • the logging mutex.
  • a shared "stop" flag (plus the mutex/cond used to publish it) — set either by the monitor on burnout, or by whichever coder thread completes the last compile needed to satisfy number_of_compiles_required for everyone.
  • a running count of how many coders have reached the required compile count.

Concurrency Protocol

The exact sequence of steps — as an outline, not compilable code.

Coder thread — one cycle

outline, not code
loop while stop-flag is not set:
    submit a combined request for (left dongle, right dongle) to the arbiter
    block on the arbiter's condition variable until:
        - both dongles are granted together, or
        - the stop-flag becomes set (exit the loop, don't start a new attempt)
    log "has taken a dongle" for each of the two dongles
    log "is compiling"
    record last_compile_start_ms = now                         <- resets the burnout deadline
    sleep/wait time_to_compile ms
    mark both dongles released (set last_release_ms = now); wake the arbiter
    log "is debugging"      ; sleep time_to_debug ms
    log "is refactoring"    ; sleep time_to_refactor ms
    increment compiles_done
    if compiles_done == number_of_compiles_required:
        atomically increment the shared "coders satisfied" counter
        if that counter now equals number_of_coders:
            set stop-flag, wake everyone
Why the deadline field updates exactly when compiling starts This mirrors the subject's literal wording: the burnout window is measured "since the beginning of their last compile." Updating it earlier (at request time) or later (at compile end) would silently change the semantics and desynchronize your simulation from the reference log examples.

Monitor thread — burnout watch

outline, not code
loop while stop-flag is not set:
    compute each coder's current deadline (last_compile_start_ms + time_to_burnout,
        or t0 + time_to_burnout if they haven't compiled yet)
    find the single earliest upcoming deadline among all coders
    pthread_cond_timedwait on the shared state-changed condition, until that deadline
    if woken early (a coder's state changed): loop back, recompute
    if the wait timed out on its own:
        re-check that specific coder: have they started compiling since?
        if not -> that coder burned out: log immediately, set stop-flag, wake everyone
        if yes -> spurious/racy wakeup near the deadline, loop back and recompute

Shutdown

Once the stop-flag is set (by either the monitor or a completing coder), every sleeping thread wakes via broadcast, observes the flag, and exits its loop cleanly — a currently-compiling coder is allowed to finish its current phase rather than being cut off, honoring the "no unexpected exits" rule. main then joins every coder thread, joins the monitor thread, destroys every mutex/condition variable, and frees every allocation, strictly in that dependency order.

Norm Checklist

The 42 Norm rules most likely to bite a concurrency project.

  • Function body ≤ 25 lines (braces excluded).
  • ≤ 5 variables declared per function; ≤ 4 parameters per function.
  • One statement per line; one variable declaration per line.
  • No for loop with multiple statements packed into init/condition/increment beyond a single simple counter; no assignment inside a condition.
  • Forbidden outright: variable-length arrays, nested functions, the ternary operator (?:), the comma operator.
  • Global variables are forbidden by the Norm independently of the subject's own ban — two reasons pointing at the same architectural decision from Phase 01.
  • ≤ 5 functions per .c file — the reason scheduler.c may need to split (Phase 11).
  • Include guards on every header; forward declarations of shared types belong in structures.h.
  • Makefile: exactly the rules NAME, all, clean, fclean, re; must not relink when nothing changed.

Your Test Harness

What stress_test.sh and test_codexion.sh actually verify.

stress_test.sh — liveness under repetition

Runs four fixed configurations (cooldowns 400/800, under both schedulers) once each, checking that no burnout occurs and that all four phase-log lines appear; then repeats each configuration 20 times in a loop, watching purely for any burnout appearing. This is a targeted liveness/fairness check — it's designed to expose an edf implementation that starves a coder only occasionally, which a single run would never catch.

test_codexion.sh — correctness, precisely

Runs the exact benchmark cases from the grading rubric (single-coder, easy fifo/edf, the infeasible burnout edge case, cooldown and contention cases, and a 50-coder large case), each repeated multiple times with a 30-second timeout, and for every produced log runs check_log:

CheckWhat it encodes
Two-dongle ruleAn awk state machine confirming every "is compiling" line was preceded by exactly two "has taken a dongle" lines for that coder — a direct, executable test of "compiling requires two dongles held simultaneously."
Burnout is the last lineOnce a coder burns out, nothing else may be logged afterward — the simulation must stop immediately.
Serialized outputA regex heuristic looking for signs of two merged log fragments on one line — a smoke test for the logging mutex.

It finishes with valgrind --leak-check=full (memory leaks) and valgrind --tool=helgrind (data races), grepping for a clean error summary. The grading rubric additionally mentions --tool=drd and compiling with -fsanitize=thread as tools an evaluator may reach for — worth running yourself before any defense.

Use these while building, not only at the end Both scripts are excellent regression tests during implementation: run them after every module lands, not just once the whole program compiles for the first time.

Roadmap

The order implementation will follow, module by module — this is what gets invoked next.

  1. Argument parsing and validation — no threads yet; prove rejection of bad input first.
  2. All struct/type definitions in structures.h, matching Phase 12 exactly.
  3. The heap in isolation — insert/extract/compare, hand-verified with printed sequences before any thread touches it.

  6. The coder thread routine, one phase at a time (request → compile → debug → refactor), compiling and testing after each phase, never all at once.
  7. The monitor thread's precise, timed-wait-based burnout detection.
  8. The shared stop-flag and the "all coders satisfied" completion path.
  9. Continuous runs of both shell scripts throughout — not saved for the end.
  10. valgrind and helgrind clean before calling any milestone done.
  11. The Makefile (NAME/all/clean/fclean/re) and a full Norm pass.
