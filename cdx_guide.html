STEP 1main() — the entry point

int main(int argc, char **argv)
{
    t_sim   sim;
    int     ret;

    memset(&sim, 0, sizeof(t_sim));
    if (parse_args(argc, argv, &sim) != 0)
        return (1);
    if (sim.compiles_required == 0)
        return (0);
    if (sim_init(&sim) != 0) { ... return (1); }
    ret = sim_run(&sim);
    sim_cleanup(&sim);
    if (ret != 0) return (1);
    return (0);
}

t_sim sim is your entire universe — one struct, allocated once on main()'s stack, that every thread you spawn later will receive a pointer to. Nothing else is global. That single design choice is why you can honestly say "no global mutable state" when the correction sheet's Global question asks about it: the coders and the monitor never touch a file-scope variable, they all dereference the same t_sim *sim passed to them.

memset(&sim, 0, sizeof(t_sim)) zero-initializes every field before anything else touches it — this matters because sim.stopped, sim.heap_size, all the pointers (coders, dongles, threads, heap, pending) start at false / 0 / NULL. If sim_init() fails halfway, sim_cleanup() can safely call free() on whatever is still NULL because every cleanup function checks the pointer before freeing it.

Three calls, three possible exits:

  • parse_args() fails → exit 1 immediately, nothing was ever allocated.
  • compiles_required == 0 → the subject's own edge case: with 0 required compiles, every coder has already "compiled 0 times" the instant the program starts, so the simulation is trivially finished before a single thread exists. Exit 0, cleanly, with zero output.
  • Otherwise: sim_init() builds every array/mutex/condvar, sim_run() actually spawns the threads and blocks until they all finish, then sim_cleanup() tears everything down unconditionally (even if sim_run() failed) — that's why ret is saved instead of returned immediately.

STEP 2parse_args() — turning argv into a t_sim

src/1_parser.c

Called with argc, argv, &sim. Internally it's a three-function pipeline:

parse_nums()
→
is_valid_uint() × 7
→
safe_atoll() × 7
→
parse_sched()

parse_nums()

First checks argc != 9 (program name + 8 real arguments) and bails with a usage message otherwise. Then it loops i from 0 to 6 over the seven numeric arguments (everything except the scheduler string) and for each one:

  1. is_valid_uint(argv[i+1]) — rejects empty strings, a lone "+", and any character outside '0'..'9' (a leading + is tolerated). This is what makes ./codexion -1 800 ... fail correctly: '-' is not a digit, so it's rejected before any arithmetic happens — you never even try to interpret a negative number.
  2. safe_atoll(argv[i+1]) — a hand-rolled atoll that accumulates digit by digit and bails with -1 the moment result > INT_MAX. That guards against integer overflow silently wrapping a huge string like 99999999999999999999 into a small, wrong, positive number.
  3. If the returned value is negative (meaning it overflowed), that argument is rejected too.

parse_sched()

A plain strcmp against "fifo" / "edf", writing sim->scheduler as the enum POLICY_FIFO or POLICY_EDF. Anything else — including your test case "random" — falls into the else branch, prints the error, and returns -1.

parse_args() itself

After parse_nums() succeeds it adds two more semantic checks that aren't just "is this a number": number_of_coders >= 1 and time_to_burnout >= 1. Only then does it call parse_sched(), and only if that succeeds does it commit the parsed values into sim's fields (sim->n, sim->time_to_burnout, etc.). This order matters for a subtle but real reason: you never partially populate sim with values that came from an otherwise-invalid command line.

Return value that steers the pipeline parse_args() returns 0 or -1. main() uses that return value as the single gate for whether sim is trustworthy enough to hand to sim_init().

STEP 3sim_init() — building the world

src/2_initializer.c

int sim_init(t_sim *sim)
{
    sim->stopped = false;
    sim->start_time_ms = get_time_ms();
    if (init_mutexes(sim) != 0) return (-1);
    if (init_dongles(sim) != 0) { ...destroy mutexes...; return (-1); }
    sim->coders = malloc(...);
    if (!sim->coders || init_coders_loop(sim) != 0) { sim_cleanup(sim); return (-1); }
    sim->threads = malloc(...);
    if (!sim->threads) { sim_cleanup(sim); return (-1); }
    return (0);
}

get_time_ms() is called for the first time here (defined in utils.c):

long long get_time_ms(void)
{
    struct timeval tv;
    gettimeofday(&tv, NULL);
    return ((long long)tv.tv_sec * 1000LL + (long long)tv.tv_usec / 1000LL);
}

It reads the wall clock via gettimeofday and folds seconds+microseconds into one millisecond-resolution long long. sim->start_time_ms is your t=0. Every log line later prints sim_elapsed(sim) = get_time_ms() - sim->start_time_ms, which is why your output starts at 0 regardless of wall-clock time.

init_mutexes()

Three global pthread_mutex_t objects are created with pthread_mutex_init(&m, NULL) (the NULL attribute argument means "default mutex type" — non-recursive, non-robust, the standard fast mutex):

MutexProtects
log_mutexstdout — guarantees no two printf calls interleave
stop_mutexthe single boolean sim->stopped
arb_mutexthe "arbitration" lock — the dongle array, the request heap, and the pending scratch array, all together

If any pthread_mutex_init call fails, the function unwinds and destroys whatever it already created before returning -1 — no half-initialized mutex is ever left behind.

init_dongles()

Allocates three arrays of length sim->n in one shot: sim->dongles, sim->heap, sim->pending. sim->heap_cap = sim->n — the request heap can never need to hold more than n entries, because there are only n coders and each one can have at most one outstanding request at a time (a coder blocks on its own request before making another). This is why the heap array is fixed-size and never needs to grow.

Then it loops over the array and calls dongle_init(&sim->dongles[i], i) — this is the first time we see the t_dongle struct populated:

void dongle_init(t_dongle *d, int id)
{
    d->id = id;
    d->in_use = false;
    d->release_time = 0;
}

release_time == 0 is a sentinel meaning "never used yet" — you'll see it checked in dongle_ready() later (Step 5) to skip the cooldown check entirely for a dongle that's brand new.

init_coders_loop() → init_coder()

For each index i in 0..n-1, init_coder fills a t_coder:

sim->coders[i].id     = i + 1;                       // human-facing id, 1-based
sim->coders[i].left   = &sim->dongles[i];
sim->coders[i].right  = &sim->dongles[(i + 1) % sim->n];
sim->coders[i].last_compile_start = sim->start_time_ms;
sim->coders[i].compile_count = 0;
sim->coders[i].ticket = 0;
sim->coders[i].granted = false;
sim->coders[i].burned_out = false;
sim->coders[i].sim = sim;

This is the whole "N coders around a circular table, N dongles between them" model: coder i (0-indexed) owns the dongle to its left at index i, and shares its right dongle with the next coder — (i + 1) % sim->n wraps the last coder's right dongle back to dongle 0, closing the circle. Special case: when n == 1, left and right both point at dongles[0] — the same dongle. That single fact is what makes the 1 800 200 200 200 10 0 fifo reference case mathematically impossible to satisfy: a coder that needs two distinct dongles but whose left and right are the same physical dongle can never complete step 1 of the ritual. It's designed to burn out.

last_compile_start is seeded to sim->start_time_ms — i.e. "the burnout clock starts ticking from t=0", not from some later moment. This is exactly why the monitor thread (Step 6) can correctly declare a burnout even for a coder that hasn't compiled even once yet.

Then, for the first time, per-coder synchronization primitives are created:

if (pthread_cond_init(&sim->coders[i].cond, NULL) != 0) return (-1);
if (pthread_mutex_init(&sim->coders[i].cond_mutex, NULL) != 0)
{ pthread_cond_destroy(&sim->coders[i].cond); return (-1); }

Every coder gets its own private condition variable + mutex pair. POSIX requires a condition variable to always be paired with the mutex that protects the predicate it waits on — you can't call pthread_cond_wait without holding a mutex. Here the predicate each coder waits on is "c->granted == true OR sim is stopped" — you'll see this used for real in Step 5.

If any coder's init fails partway through the loop, init_coders_loop walks backwards from the failure point (while (--i >= 0) destroy...), destroying only the cond/mutex pairs that were actually created, before freeing the coders array and returning -1. That backward-unwind pattern is the correct, leak-free way to fail out of a partially-completed loop of resource acquisitions.

Back in sim_init()

Finally, sim->threads = malloc(sim->n * sizeof(pthread_t)) — just reserved storage for the pthread_t handles that pthread_create() will fill in during Step 4. If this allocation fails, sim_cleanup(sim) (Step 7) is invoked directly from here — which is exactly why sim_cleanup() has to be defensive about every pointer being possibly NULL.

Return value that steers the pipeline sim_init() returns 0 only if every mutex, condvar, and allocation in the chain succeeded. main() treats any non-zero return as fatal and never calls sim_run().

STEP 4sim_run() — spawning the threads

src/3_simulator.c

int sim_run(t_sim *sim)
{
    if (start_coders(sim) != 0) return (-1);
    if (pthread_create(&sim->monitor_thread, NULL, monitor_routine, sim) != 0)
    { ...stop, join coders, return (-1); }
    i = 0;
    while (i < sim->n) pthread_join(sim->threads[i++], NULL);
    pthread_join(sim->monitor_thread, NULL);
    return (0);
}

Before spawning threads, two tiny helpers appear that will be called constantly from now on:

bool sim_is_stopped(t_sim *sim)
{
    bool stopped;
    pthread_mutex_lock(&sim->stop_mutex);
    stopped = sim->stopped;
    pthread_mutex_unlock(&sim->stop_mutex);
    return (stopped);
}
void sim_stop(t_sim *sim)
{
    pthread_mutex_lock(&sim->stop_mutex);
    sim->stopped = true;
    pthread_mutex_unlock(&sim->stop_mutex);
}

This is the textbook fix for the classic "just read a bool from multiple threads" data race: without the mutex, one thread's write to stopped is not guaranteed to become visible to another thread's read in any bounded time (compilers/CPUs may cache it in a register), and a plain read/write pair on a shared variable without synchronization is undefined behavior in C's memory model regardless of whether it "usually works". Every single access to sim->stopped anywhere in the codebase goes through one of these two functions — there is no raw sim->stopped read outside of them.

start_coders()

Loops i from 0 to n-1 calling:

pthread_create(&sim->threads[i], NULL, coder_routine, &sim->coders[i])

pthread_create's four arguments: where to store the new thread's id, thread attributes (NULL = default — joinable, default stack size), the function the new thread will start executing (coder_routine), and the single void * argument passed to it — here, a pointer to that coder's own t_coder slot. This is the moment n independent threads start running concurrently, each with its own call stack but all sharing the same t_sim through its sim pointer. If any pthread_create fails mid-loop, the code stops the simulation and joins the threads it already managed to start, cleaning up rather than leaking live threads.

After all coder threads exist, one more thread is created: the monitor (monitor_routine, argument sim itself — the monitor doesn't belong to any single coder). So at the end of sim_run()'s setup phase you have n + 1 threads running concurrently: n coders and 1 monitor, all racing against each other, all synchronized purely through the mutexes/condvars set up in Step 3.

sim_run() then blocks on pthread_join() for every coder thread in order, and finally for the monitor thread. pthread_join makes the calling thread (main) sleep until the target thread returns — this is how main() knows the whole simulation is actually finished before moving on to sim_cleanup().

STEP 5coder_routine() — the life of one coder thread

src/4_coder.c

void *coder_routine(void *arg)
{
    t_coder *c = (t_coder *)arg;
    t_sim   *sim = c->sim;
    while (!sim_is_stopped(sim))
        if (!coder_cycle(c, sim)) break;
    return (NULL);
}

This is the whole state machine: keep running compile→debug→refactor cycles until either the simulation is globally stopped, or coder_cycle itself says "no more work for you" (returns false). coder_cycle is the actual per-cycle logic:

static bool coder_cycle(t_coder *c, t_sim *sim)
{
    pthread_mutex_lock(&c->cond_mutex);
    if (c->compile_count >= sim->compiles_required)
    { pthread_mutex_unlock(&c->cond_mutex); return (false); }
    pthread_mutex_unlock(&c->cond_mutex);
    if (!take_dongles(c)) return (false);
    run_compile_phase(c, sim);
    if (!run_debug_refactor(c, sim)) return (false);
    pthread_mutex_lock(&c->cond_mutex);
    c->compile_count++;
    pthread_mutex_unlock(&c->cond_mutex);
    return (true);
}

Note compile_count is read/written exclusively under c->cond_mutex here — that's the same mutex the monitor thread will lock in Step 6 to read this exact field. Every access to compile_count and last_compile_start across the whole program goes through this lock, on both the writer side (the coder) and the reader side (the monitor). That's a real, complete data-race fix — not just "practically fine on x86".

5.1 — take_dongles(c): acquiring both resources

static bool take_dongles(t_coder *c)
{
    if (sim_is_stopped(c->sim)) return (false);
    if (c->sim->n == 1)
    {
        pthread_mutex_lock(&c->sim->arb_mutex);
        c->left->in_use = true;
        pthread_mutex_unlock(&c->sim->arb_mutex);
        log_event(c->sim, c->id, "has taken a dongle");
        pthread_mutex_lock(&c->cond_mutex);
        while (!sim_is_stopped(c->sim))
            pthread_cond_wait(&c->cond, &c->cond_mutex);
        pthread_mutex_unlock(&c->cond_mutex);
        return (false);
    }
    c->ticket = get_time_ms();
    dongle_request(c->sim, c);
    if (sim_is_stopped(c->sim)) return (false);
    log_event(c->sim, c->id, "has taken a dongle");
    log_event(c->sim, c->id, "has taken a dongle");
    return (true);
}
Why two log lines The correction sheet's "Less easy" benchmark explicitly checks that every "is compiling" line is immediately preceded by exactly two "has taken a dongle" lines for the same coder — one per dongle. You satisfy this literally: after a single successful dongle_request() call (which internally reserves both dongles atomically, see 5.2), you log the acquisition twice, once conceptually for the left dongle and once for the right. This is a logging convention, not two separate acquisition operations — the real, race-safe acquisition already happened as one atomic step inside dongle_request().

The n == 1 branch is a dead end by design: it marks its one dongle in use, logs it took a dongle (only once — there's only one dongle to report), and then just parks on its own condition variable forever, until the simulation is stopped (which will happen — see the burnout defense in Section 11). It returns false unconditionally once woken, which propagates all the way up and ends the thread.

5.2 — dongle_request(): the heart of the arbitration system

src/5_dongle.c

void dongle_request(t_sim *sim, t_coder *c)
{
    t_request req;
    req.coder_id = c->id;
    req.priority = c->ticket;
    if (sim->scheduler == POLICY_EDF)
        req.priority = c->last_compile_start + sim->time_to_burnout;
    pthread_mutex_lock(&c->cond_mutex);
    c->granted = false;
    pthread_mutex_unlock(&c->cond_mutex);
    pthread_mutex_lock(&sim->arb_mutex);
    heap_push(sim, req);
    dispatch(sim);
    pthread_mutex_unlock(&sim->arb_mutex);
    if (!coder_wait_grant(sim, c))
    {
        pthread_mutex_lock(&sim->arb_mutex);
        idx = heap_find(sim, c->id);
        if (idx != -1) heap_remove(sim, idx);
        pthread_mutex_unlock(&sim->arb_mutex);
    }
}

First, the coder builds a request ticket: t_request { priority, coder_id }. The priority depends on the scheduler:

  • FIFO: priority = c->ticket, which was set one line earlier in take_dongles to get_time_ms() — literally "the wall-clock time this request was made". The smallest timestamp = the oldest request = served first. That's arrival-order fairness.
  • EDF (Earliest Deadline First): priority = last_compile_start + time_to_burnout — the exact millisecond this coder will burn out if it doesn't get served. The coder closest to burning out gets priority, regardless of when it asked.

Then c->granted = false is reset under c->cond_mutex before the request is even pushed into the shared heap. This ordering is not an accident — see the race-condition callout below.

The actual submission is one atomic transaction under arb_mutex: heap_push(sim, req) followed immediately by dispatch(sim), both while holding the same lock. This means: from the moment the request enters the shared queue to the moment the system decides whether it can be granted right now, no other thread can touch the heap or the dongle states in between. There's no window where the request is "half-queued".

The lost-wakeup race that this code correctly avoids A classic condition-variable bug: thread A checks "is my flag set? no" then goes to sleep — but thread B sets the flag and signals in between the check and the sleep, and the signal is lost forever because nobody was listening yet. Here it can't happen, because the flag (c->granted) is only ever read or written while holding c->cond_mutex, on both sides: coder_wait_grant() (the waiter) locks cond_mutex, then loops while (!c->granted && !stopped) pthread_cond_wait(...) — and pthread_cond_wait atomically unlocks the mutex and sleeps as one indivisible kernel operation. grant_request() (the signaler, see 5.2b) also locks the very same cond_mutex before setting granted = true and calling pthread_cond_signal. So even in the worst-case scheduling — the grant happens the instant after the heap push, before the coder thread has even reached coder_wait_grant() — the flag is already true by the time the coder locks the mutex and checks the while condition, so it simply never enters pthread_cond_wait at all. No wakeup is ever "lost" because the state (granted) is persistent, not a one-shot pulse.

heap_push(), req_less(), heap_sift_up() — first appearance

src/6_heap.c

Your request queue is a classic binary min-heap stored in a flat array (sim->heap), which is the standard array representation: for a node at index idx, its children live at 2*idx+1 and 2*idx+2, and its parent at (idx-1)/2. This gives you an O(log n) insert and an O(log n) pop-the-most-urgent-request, versus O(n) for a linear scan — and since n is small here it's mostly about correctness and clarity rather than raw speed, but it's the textbook right tool for "always process the smallest-priority item next", i.e. a priority queue.

int req_less(const t_request *a, const t_request *b)
{
    if (a->priority != b->priority) return (a->priority < b->priority);
    return (a->coder_id > b->coder_id);
}

The comparator: lower priority value wins (both FIFO timestamps and EDF deadlines are "smaller = more urgent", so this one comparator correctly serves both scheduling policies just by changing what number goes into priority). If two requests tie exactly on priority, the higher coder_id is treated as "less" — an arbitrary but deterministic tie-break, which matters because a non-deterministic tie-break could occasionally produce a different grant order between otherwise identical runs, which is exactly the flakiness the correction sheet warns evaluators to watch for.

int heap_push(t_sim *sim, t_request req)
{
    if (sim->heap_size >= sim->heap_cap) return (-1);
    sim->heap[sim->heap_size] = req;
    heap_sift_up(sim->heap, sim->heap_size);
    sim->heap_size++;
    return (0);
}

Appends the new request at the next free slot, then heap_sift_up repeatedly swaps it with its parent while it's "less" (more urgent) than the parent, restoring the heap invariant in O(log n) swaps. This can never overflow because heap_cap == sim->n and, as noted above, at most one request per coder can be in flight at once.

dispatch() — deciding who actually gets to compile

void dispatch(t_sim *sim)
{
    t_request req; t_coder *c; int pending = 0;
    while (sim->heap_size > 0)
    {
        req = sim->heap[0];
        heap_remove(sim, 0);
        c = &sim->coders[req.coder_id - 1];
        if (c->left != c->right
            && dongle_ready(c->left, sim->dongle_cooldown)
            && dongle_ready(c->right, sim->dongle_cooldown))
            grant_request(c);
        else
            sim->pending[pending++] = req;
    }
    while (pending > 0)
        heap_push(sim, sim->pending[--pending]);
}

This is the piece that decides everything. It fully drains the heap, one request at a time, always popping index 0 — which, in a min-heap, is always the single most urgent pending request. For each one it asks: are both of this coder's dongles currently free and past their cooldown? If yes, grant_request(c) hands them over right now, atomically, as a pair. If no, the request is parked in the pending scratch array instead of being lost. Once every queued request has been examined exactly once (in strict priority order), whatever couldn't be granted is pushed back into the heap.

heap_remove(sim, 0) (also in 6_heap.c) is what actually pops the root: it moves the last element of the heap into the vacated root slot, shrinks heap_size, and then runs both heap_sift_up and heap_sift_down on that relocated element, because depending on its priority it might need to move either up or down to restore the heap property — a single direction isn't guaranteed to be correct after an arbitrary removal.

Why the whole heap is drained every single call instead of just checking the top request: because granting one request can never make an earlier, still-pending request grantable (dongles only get scarcer as you grant more), so a naive "pop top, if not grantable stop" would systematically starve any request sitting behind a currently-blocked one, even if that request's own two dongles happen to be perfectly free. Draining the whole heap in strict priority order and re-queuing only the actually-unsatisfiable ones guarantees maximum parallelism on every call: every coder whose two dongles are free right now gets served in this pass, regardless of position in the queue.

bool dongle_ready(t_dongle *d, long long cooldown_ms)
{
    if (d->in_use) return (false);
    if (d->release_time == 0) return (true);
    return (get_time_ms() >= d->release_time + cooldown_ms);
}

A dongle is ready if it's not currently held, and either it's never been used (release_time == 0, the sentinel from Step 3) or enough time has passed since its last release to satisfy dongle_cooldown.

void grant_request(t_coder *c)
{
    c->left->in_use = true;
    c->right->in_use = true;
    pthread_mutex_lock(&c->cond_mutex);
    c->granted = true;
    pthread_cond_signal(&c->cond);
    pthread_mutex_unlock(&c->cond_mutex);
}

Both dongles flip to in_use = true in the same statement pair, still under arb_mutex (held by the caller, dispatch(), which is itself always called while arb_mutex is locked). This is the crucial detail for deadlock-freedom — see Section 8. Then the coder's own granted flag is flipped and its private condition variable is signaled, waking it up from coder_wait_grant() if it's already sleeping there, or pre-setting the flag if it hasn't gotten there yet (per the lost-wakeup discussion above).

coder_wait_grant() — the coder actually goes to sleep

src/7_helper.c

bool coder_wait_grant(t_sim *sim, t_coder *c)
{
    pthread_mutex_lock(&c->cond_mutex);
    while (!c->granted && !sim_is_stopped(sim))
        pthread_cond_wait(&c->cond, &c->cond_mutex);
    got = c->granted;
    pthread_mutex_unlock(&c->cond_mutex);
    return (got);
}

This blocks the coder thread — using zero CPU while waiting, unlike a busy-poll loop — until either it gets granted its dongles, or the whole simulation stops (because someone else burned out, or everyone finished). The while loop (not an if) around pthread_cond_wait is mandatory POSIX practice: condition variables can wake up "spuriously" (with no corresponding signal at all), so you must always re-check the actual predicate after waking, not just trust that being woken means the condition is true.

Return value that steers the pipeline: if the wait returns because the simulation stopped rather than because of a real grant, dongle_request() (5.2) removes this coder's now-orphaned request from the shared heap under arb_mutex, using heap_find() (linear scan for this coder_id) followed by heap_remove(). This prevents a stale, never-to-be-granted request from sitting in the heap after the coder that submitted it has already given up.

5.3 — run_compile_phase(): actually "compiling"

static void run_compile_phase(t_coder *c, t_sim *sim)
{
    pthread_mutex_lock(&c->cond_mutex);
    c->last_compile_start = get_time_ms();
    pthread_mutex_unlock(&c->cond_mutex);
    log_event(sim, c->id, "is compiling");
    msleep(sim->time_to_compile);
    put_dongles(c);
}

The instant it starts compiling, last_compile_start is stamped with the current time — this resets the burnout clock. That's the whole meaning of the rule "must start a new compile within time_to_burnout ms of the last one": the deadline is always measured from this exact field, written here and only here (besides the initial seed in Step 3), and always under cond_mutex so the monitor thread's concurrent reads of it are never torn or stale beyond one lock hand-off.

msleep() (in utils.c) is your busy-work simulator:

int msleep(long long ms)
{
    deadline = get_time_ms() + ms;
    while (1)
    {
        now = get_time_ms();
        if (now >= deadline) return (0);
        remaining = deadline - now;
        if (remaining > 1000) remaining = 1000;
        usleep((useconds_t)(remaining * 1000LL));
    }
}

Rather than a single usleep(ms*1000), it loops, sleeping in chunks of at most 1 second and re-checking the actual elapsed wall-clock time each time. This protects against usleep's documented imprecision on long sleeps and against being woken early by a signal — it guarantees you never return before the deadline, only ever at or slightly after it (see Section 11 for exactly how much "slightly" is and why that's fine).

After the compile-duration sleep, put_dongles(c) is a one-line wrapper around dongle_release(c->sim, c):

void dongle_release(t_sim *sim, t_coder *c)
{
    pthread_mutex_lock(&sim->arb_mutex);
    c->left->in_use = false;
    c->left->release_time = get_time_ms();
    if (c->right != c->left)
    {
        c->right->in_use = false;
        c->right->release_time = get_time_ms();
    }
    dispatch(sim);
    pthread_mutex_unlock(&sim->arb_mutex);
}

Both dongles are freed and stamped with the current time as their new release_time (which starts their cooldown clock), and then — still under the same lock — dispatch() is called again immediately. This is exactly how a released dongle gets handed to the next waiting coder without any delay: the very act of releasing triggers a fresh arbitration pass right there, in the releasing thread, rather than waiting for some other thread to notice.

5.4 — run_debug_refactor(): the rest of the cycle

static bool run_debug_refactor(t_coder *c, t_sim *sim)
{
    if (sim_is_stopped(sim)) return (false);
    log_event(sim, c->id, "is debugging");   msleep(sim->time_to_debug);
    if (sim_is_stopped(sim)) return (false);
    log_event(sim, c->id, "is refactoring"); msleep(sim->time_to_refactor);
    return (true);
}

Plain sequential logging + sleeping, with a sim_is_stopped() check before each phase so a coder doesn't keep logging fake progress after the simulation has already ended elsewhere (e.g. because another coder burned out mid-cycle). Note the dongles are already released by this point (released right after the compile phase) — the coder only needs both dongles for the compile itself, freeing them immediately afterward is exactly what lets other coders make progress during this coder's debug/refactor time.

Back in coder_cycle: if this returns true, compile_count is incremented under cond_mutex and the whole cycle repeats from the top of coder_routine's while loop — check the stop flag, check the compile quota, request dongles again with a fresh ticket (for FIFO) or a later deadline (for EDF, since last_compile_start just advanced).

Eventually one of three things ends this thread: the quota check at the top of coder_cycle sees compile_count >= compiles_required and returns false; take_dongles returns false because the sim was already stopped by someone else; or run_debug_refactor returns false for the same reason. Any of these breaks the outer while loop in coder_routine, which returns NULL — the thread is done, waiting to be joined.

STEP 6monitor_routine() — the referee thread

src/8_monitor.c & src/utils2.c

This thread is created right after the coders (Step 4) and runs concurrently with all of them for the entire simulation. Its job is everything that no single coder can know on its own: "has everyone finished?", "has anyone silently blown their deadline?", and "did a cooldown expire while nobody was actively watching?"

void *monitor_routine(void *arg)
{
    t_sim *sim = (t_sim *)arg;
    while (!sim_is_stopped(sim))
    {
        wake_us = monitor_tick(sim);
        if (wake_us < 0) break;
        usleep((useconds_t)wake_us);
    }
    return (NULL);
}

Every iteration: run one full monitor_tick(), then sleep for exactly as long as monitor_tick itself calculated is safe to sleep before something needs to be re-checked. A negative return means "the simulation just ended, stop looping".

monitor_tick()

long long monitor_tick(t_sim *sim)
{
    if (sim->compiles_required > 0 && all_compiled(sim))
    { handle_stop(sim, 0); return (-1); }
    pthread_mutex_lock(&sim->arb_mutex);
    dispatch(sim);
    pthread_mutex_unlock(&sim->arb_mutex);
    burned = scan_coders(sim, &wake_us);
    if (burned != 0) { handle_stop(sim, burned); return (-1); }
    cooldown_us = next_cooldown_us(sim);
    if (cooldown_us < wake_us) wake_us = cooldown_us;
    return (wake_us);
}

6.1 — all_compiled()

bool all_compiled(t_sim *sim)
{
    while (i < sim->n)
    {
        pthread_mutex_lock(&sim->coders[i].cond_mutex);
        count = sim->coders[i].compile_count;
        pthread_mutex_unlock(&sim->coders[i].cond_mutex);
        if (count < sim->compiles_required) return (false);
        i++;
    }
    return (true);
}

Locks each coder's own cond_mutex individually just to read its compile_count — the same lock the coder thread uses when it increments that field (Step 5, end of coder_cycle). This is the successful-completion path: as soon as every coder has hit the required count, handle_stop(sim, 0) is called (a "0" burned-coder id means "clean stop, nobody burned out"), and monitor_tick returns -1, ending the monitor loop.

6.2 — the periodic re-dispatch

If not everyone's done, the monitor grabs arb_mutex and calls dispatch() itself — the exact same function coders call when they submit or release a request (5.2 / 5.3). Why does the monitor also need to call it? Because a dongle's cooldown expiring is a silent, time-based event: nothing "happens" at that exact millisecond from any thread's point of view unless something actively checks the clock. If coder A released a dongle and went off to debug/refactor, and coder B is the only one waiting on that dongle, nobody will re-run dispatch() when the cooldown finally elapses unless the monitor does it on a timer. This periodic tick is exactly that safety net.

6.3 — scan_coders() and coder_deadline_remain(): burnout detection

long long coder_deadline_remain(t_sim *sim, int i, long long now)
{
    pthread_mutex_lock(&sim->coders[i].cond_mutex);
    start = sim->coders[i].last_compile_start;
    count = sim->coders[i].compile_count;
    pthread_mutex_unlock(&sim->coders[i].cond_mutex);
    if (count >= sim->compiles_required) return (1000000000LL);
    return (start + sim->time_to_burnout - now);
}

A coder that's already reached its compile quota is given an effectively infinite deadline (1e9 ms) so it can never trigger a false burnout after it's already "retired" from the race. Otherwise, the remaining time is exactly last_compile_start + time_to_burnout - now: if that's <= 0, the coder has failed to start a new compile in time.

int scan_coders(t_sim *sim, long long *wake_us)
{
    now = get_time_ms(); *wake_us = 10 * 1000LL; burned = 0;
    while (i < sim->n)
    {
        remain = coder_deadline_remain(sim, i, now);
        if (remain <= 0 && burned == 0) burned = i + 1;
        if (remain * 1000LL < *wake_us) *wake_us = remain * 1000LL;
        i++;
    }
    if (*wake_us < 200) *wake_us = 200;
    return (burned);
}

Two jobs at once, in one pass over every coder: (1) find the first coder (lowest index) whose deadline has already passed, remembering it as burned; (2) compute, in microseconds, how long until the soonest upcoming deadline among all coders — this becomes the monitor's next usleep duration, clamped to a minimum of 200 µs so it never busy-spins even if a deadline is already in the past by the time this runs. This adaptive sleep is the key to precise-but-cheap burnout detection: the monitor doesn't poll at a fixed fast interval burning CPU the whole time, it computes exactly how long it can safely sleep before it needs to check again, and sleeps that long, no more.

6.4 — next_cooldown_us(): waking up exactly when a dongle becomes usable

long long next_cooldown_us(t_sim *sim)
{
    now = get_time_ms(); nearest = 10 * 1000LL;
    pthread_mutex_lock(&sim->arb_mutex);
    while (i < sim->n)
    {
        if (!sim->dongles[i].in_use && sim->dongles[i].release_time != 0)
        {
            remain = sim->dongles[i].release_time + sim->dongle_cooldown - now;
            if (remain > 0 && remain * 1000LL < nearest) nearest = remain * 1000LL;
        }
        i++;
    }
    pthread_mutex_unlock(&sim->arb_mutex);
    return (nearest);
}

Scans every idle-but-still-cooling dongle and finds the soonest moment any of them exits cooldown. monitor_tick then takes min(deadline_wake_us, cooldown_wake_us) — the monitor always sleeps only as long as the more urgent of "next possible burnout" or "next possible dongle becoming available", guaranteeing it wakes up in time to react to either kind of event, and calls dispatch() again right after waking.

6.5 — handle_stop() and wake_all_coders(): shutting everything down cleanly

void handle_stop(t_sim *sim, int burned)
{
    sim_stop(sim);
    if (burned != 0) log_burnout(sim, burned);
    wake_all_coders(sim);
}

sim_stop() flips the global flag (Step 4) before anything else. Note log_burnout() computes its timestamp before taking log_mutex (see utils.c) — the elapsed time is captured as close as possible to the actual detection moment, not delayed by however long it takes to acquire the print lock.

void wake_all_coders(t_sim *sim)
{
    signal_coders(sim);                          // pass 1
    pthread_mutex_lock(&sim->arb_mutex);
    pthread_mutex_unlock(&sim->arb_mutex);
    signal_coders(sim);                          // pass 2
}

signal_coders() loops every coder, locks its cond_mutex, calls pthread_cond_broadcast (wake every thread waiting on this condvar, not just one — safe here because at most one thread ever waits on a given coder's condvar anyway), and unlocks. The double broadcast, with an arb_mutex lock/unlock sandwiched in between, is deliberate: a coder that is, at this exact instant, inside dongle_request() holding arb_mutex but hasn't yet reached coder_wait_grant() could miss the first broadcast entirely (it isn't waiting on the condvar yet). Acquiring and releasing arb_mutex here forces the monitor to wait until any coder mid-way through that critical section has finished it and moved on (to either being granted, or about to wait), and the second broadcast then reliably catches it once it does start waiting. Combined with the persistent-flag design from 5.2's lost-wakeup discussion, this makes the shutdown signal essentially un-missable.

STEP 7Joining, and sim_cleanup()

src/9_cleaner.c

Back in sim_run() (Step 4), once every coder thread has returned NULL (its while loop broke, for any of the three reasons in 5.4) and the monitor has also returned (because monitor_tick returned -1), all the pthread_join calls unblock and sim_run() returns to main(). main() then unconditionally calls sim_cleanup(sim):

void sim_cleanup(t_sim *sim)
{
    if (sim->threads) { free(sim->threads); sim->threads = NULL; }
    if (sim->coders) free_coders(sim);
    if (sim->dongles) free_dongle_arrays(sim);
    pthread_mutex_destroy(&sim->log_mutex);
    pthread_mutex_destroy(&sim->stop_mutex);
    pthread_mutex_destroy(&sim->arb_mutex);
}

free_coders() loops every coder destroying its cond and cond_mutex (mirror image of init_coder in Step 3) before freeing the array itself. free_dongle_arrays() frees the three parallel arrays (dongles, heap, pending) that were all allocated together in init_dongles. Every pointer is set back to NULL after freeing — cheap insurance against any accidental double-free, and consistent with the "everything starts zeroed" guarantee from main()'s initial memset. This symmetric init/cleanup pairing (every _init has a matching destroy, every malloc a matching free, called from a single unconditional cleanup path reachable from every failure branch) is exactly what makes this leak-free under valgrind, including on the early-exit paths in sim_init() itself.

Finally, control returns to main(), which returns 1 if sim_run() reported failure or 0 otherwise. Program exits.

8. Deep dive — concurrency safety, Coffman conditions, races, starvation

8.1 — Deadlock: how the four Coffman conditions are actually broken here

ConditionPresent?Why / how it's handled
Mutual exclusionYes (unavoidable) A dongle really can only serve one coder at a time — that's the problem definition, not a bug.
Hold-and-waitNo — this is the actual fix A coder never holds one dongle while waiting for the second. Look again at grant_request(): c->left->in_use = true; c->right->in_use = true; both flip together, inside dispatch(), inside a single critical section under arb_mutex. A request is only ever granted when both dongles are simultaneously free (dongle_ready(left) && dongle_ready(right)) — there is no code path anywhere that marks one dongle in-use and then separately tries to acquire the other. The coder thread doesn't even see its dongles as "acquired" one at a time; from its perspective it calls dongle_request() once and either gets both or gets neither.
No preemptionYes (by design, and fine) Dongles are only ever released voluntarily by dongle_release() after a compile finishes — nobody forcibly strips a dongle from a coder. This condition is allowed to hold because condition 2 (the dangerous one) is already eliminated.
Circular waitNo — impossible given the above A circular wait (A holds X, wants Y; B holds Y, wants X) fundamentally requires partial holding — some thread holding one resource while blocked wanting another. Since no coder ever holds a dongle while waiting for a second one, the wait-for graph among coders never contains an edge from a coder that's currently holding anything. No holder ever waits, so no cycle of holders-waiting-for-each-other can form.
How to phrase this to an evaluator "I don't prevent deadlock via lock ordering or a resource hierarchy — I prevent it by making resource acquisition atomic and all-or-nothing. All admission decisions for every coder happen inside one critical section, protected by one mutex (arb_mutex), and a coder is only ever moved from 'holds nothing' to 'holds both dongles' in a single step. There is no intermediate state where a thread holds exactly one of the two dongles it needs, so Coffman condition 2 (hold-and-wait) never holds, and therefore condition 4 (circular wait) can't either — which is sufficient on its own to rule out deadlock, since all four conditions must hold simultaneously for a deadlock to occur."

8.3 — Starvation prevention

  • FIFO: priority = request timestamp. Because the min-heap always serves the smallest timestamp first and dispatch() re-evaluates the entire queue on every call rather than only looking at the front, a request can only be repeatedly skipped if its own two specific dongles keep being unavailable — it is never skipped in favor of a later request whose dongles happen to be free while its own aren't (that's not starvation, that's the actual resource constraint). Among requests contending for the same dongles, strict arrival order is preserved.
  • EDF: priority = absolute burnout deadline, which strictly increases every time that specific coder completes a compile (because it's derived from the ever-advancing last_compile_start). A coder that keeps losing arbitration keeps the same, increasingly urgent deadline, so it becomes more and more likely to win as its situation gets more dangerous — the scheduler is explicitly biased to protect the coder closest to failing.

9. README vs reality — what to actually say in defense

Read this before your defense Your README.md's "Blocking cases handled" section makes a few claims that are not what src/ actually does. If an evaluator reads both the README and the code side by side (the correction sheet explicitly tells them to "read the code to confirm"), you want to describe the real mechanism, not the README's wording — the real mechanism is actually stronger and easier to defend.
README claimsWhat the code actually does
"Circular wait broken by always acquiring dongles in ascending id order." There is no per-dongle acquisition order at all — grant_request() takes both dongles simultaneously in one atomic step, so hold-and-wait (condition 2) never occurs, which rules out circular wait directly. See Section 8.1.
"Each dongle has a mutex" / "pthread_mutex_t dongle.mutex". There is no per-dongle mutex in t_dongle — every dongle's state is protected by the single shared arb_mutex. Simpler, and correct, but say arb_mutex, not "dongle.mutex", if asked to point at the code.
"A waiting coder re-checks with a 0.5 ms pthread_cond_timedwait." coder_wait_grant() uses a plain, untimed pthread_cond_wait. The coder never polls at all — it's the monitor thread that periodically calls dispatch() (driven by next_cooldown_us()'s calculation) and it is the monitor, via grant_request(), that wakes the coder exactly when its dongles actually become available. There is no cooldown-driven timed-wait anywhere in dongle.c or helper.c.
"A staggered start (even-numbered coders sleep time_to_compile/2 ms) prevents a thundering herd at startup." coder_routine() has no start-up delay of any kind — every coder thread calls take_dongles() immediately. The thundering herd at t=0 is instead absorbed safely by arb_mutex: all n coders may race to submit their first request simultaneously, but heap_push + dispatch only ever run one at a time (mutex-serialized), so the burst is resolved correctly and deterministically by priority, just not pre-emptively spread out in time.

None of these discrepancies are bugs — the actual implementation satisfies every requirement on the correction sheet using a simpler, centralized, atomic-arbitration design. Just make sure your spoken explanation matches arb_mutex + dispatch(), not the README's older/aspirational wording.

10. Live recode — turning "fifo" into "lifo"

The correction sheet's recode exercise asks you to make the most recently arrived waiting request win, instead of the oldest. Two things must change, and only two — and critically, the change must live in the actual scheduling comparison, not in how you print the logs (the guideline explicitly says to verify this by reading the code).

Step A — teach the parser a third scheduler word

// codexion.h
typedef enum e_scheduler { POLICY_FIFO, POLICY_EDF, POLICY_LIFO } t_scheduler;

// 1_parser.c, parse_sched()
if (strcmp(s, "fifo") == 0) sim->scheduler = POLICY_FIFO;
else if (strcmp(s, "edf") == 0) sim->scheduler = POLICY_EDF;
else if (strcmp(s, "lifo") == 0) sim->scheduler = POLICY_LIFO;
else { fprintf(stderr, "Error: scheduler must be 'fifo', 'edf' or 'lifo'.\n"); return (-1); }

Step B — flip the actual priority number in dongle_request()

Recall req_less() always treats the smaller priority value as more urgent — that's what makes it a min-heap. For FIFO you want the oldest (smallest) timestamp to win, which is exactly what happens when priority = ticket. For LIFO you want the newest (largest) timestamp to win — so you need the newest ticket to map to the smallest priority number. Negate it:

// 5_dongle.c, dongle_request()
req.coder_id = c->id;
req.priority = c->ticket;
if (sim->scheduler == POLICY_EDF)
    req.priority = c->last_compile_start + sim->time_to_burnout;
else if (sim->scheduler == POLICY_LIFO)
    req.priority = -c->ticket;   // larger (more recent) ticket ⇒ smaller priority ⇒ served first

That's it. No change to req_less, heap_sift_up/down, dispatch(), or any logging function — the entire scheduling policy is a one-line change of what number goes into priority. This is exactly why the correction sheet can tell whether you faked it at the log level: if you had only reversed the order lines are printed, the underlying grant order (which dongles actually got flipped to in_use and when) would still match old FIFO order — but with this change, the real timestamps at which "has taken a dongle" lines appear for each coder will genuinely reverse.

Step C — verifying the recode is real, not cosmetic

Run the exact contention-heavy case from the correction sheet before and after the change:

./codexion 5 3000 200 200 200 10 800 fifo   # baseline: arrival order
./codexion 5 3000 200 200 200 10 800 lifo   # after the recode

Because dongle_cooldown = 800 is large relative to the phase durations, several coders will genuinely queue up waiting for a dongle at the same time. Grep the output for "has taken a dongle" lines and look at which coder_id gets served first among a group that queued up together: under fifo it should be whoever asked earliest; under lifo it should be whoever asked last among that same waiting group — a genuine reversal of the observed grant order, not just of the text in the log. You can point directly at req.priority = -c->ticket; in the source as the one line responsible, which is what "confirm the change is made in the scheduler/queue logic itself" is asking you to be able to do.

11. Defense script — why the burnout timestamp isn't exactly on the deadline

Two separate things are worth being able to explain clearly here, because the correction sheet raises both: (a) why certain reference cases are designed to burn out at all, and (b) why the printed timestamp lands a few milliseconds after the theoretical deadline rather than on it, exactly.

11.1 — Why ./codexion 1 800 200 200 200 10 0 fifo and ./codexion 5 500 200 200 200 10 0 fifo must burn out — this is math, not timing luck

These aren't cases where "something might go wrong" — they're constructed to be infeasible by construction, independent of any OS scheduling behavior:

  • The single-coder case: with n == 1, init_coder sets c->left = &dongles[0] and c->right = &dongles[(0+1)%1] = &dongles[0] — the same dongle object. A compile needs two distinct dongles held simultaneously; there is only one dongle in existence. No amount of correct scheduling can conjure a second physical resource. Burnout at ~800 ms is a direct, deterministic consequence of the resource math, not of scheduling variance.
  • The 5 500 ... case: one full cycle costs at minimum time_to_compile + time_to_debug + time_to_refactor = 200+200+200 = 600 ms of guaranteed work before a coder can even attempt its next compile — and that's the best possible case, assuming zero wait time for dongles. But time_to_burnout = 500 ms, which is strictly less than 600. Even a coder that gets its dongles instantly, every single time, with zero contention, cannot mathematically start its next compile before its own deadline expires. This is guaranteed to happen to every coder, so the first one the monitor's scan encounters (lowest coder id, per scan_coders's i + 1 tie-break, which is not itself scheduling-dependent) is reported. It happens "around timestamp 500" — not because of OS jitter, but because 500 is the deadline, seeded at t=0 in init_coder.

11.2 — Why the printed line still lands a few ms after 500, not at exactly 500

This is the actual OS-scheduling story, and it's a completely different, much smaller effect layered on top of the deterministic burnout above. Three real sources of delay, all present in this codebase and all bounded:

  1. Monitor polling granularity. The monitor doesn't watch the clock continuously — it sleeps for wake_us microseconds (from scan_coders/next_cooldown_us, floor-clamped to 200 µs) and only re-checks deadlines when it wakes up. So detection happens at the next scheduled wake-up after the deadline passes, not at the exact microsecond it passes. Since scan_coders recomputes the time-to-next-deadline on every tick and always sleeps for at most that long (clamped to at least 200 µs so it doesn't busy-spin), the monitor is guaranteed to wake up within roughly one clamped interval of the true deadline — on the order of a fraction of a millisecond to a couple of milliseconds in practice, comfortably inside the sheet's stated 10 ms tolerance.
  2. Kernel scheduling latency on usleep. usleep() is a request for "at least this long", never a guarantee of exactly that long — the OS scheduler only guarantees to wake the thread at or after the requested time, and the actual wake-up depends on what else is running, timer interrupt granularity, and how loaded the machine is. This is precisely the "slow hardware" / "OS scheduling" variance the correction sheet tells evaluators to tolerate. Your own msleep() already compensates for this on the coder side by re-checking get_time_ms() in a loop instead of trusting a single usleep call to be exact — the monitor's own usleep(wake_us) doesn't need the same loop because slightly overshooting its sleep only delays detection by a similarly small amount, it never causes a false-negative (a burnout that should've fired but didn't) or a false-positive.
  3. log_mutex contention. Between the monitor detecting the burnout and the line actually reaching stdout, log_burnout() must acquire log_mutex. If some coder thread happens to be mid-log_event() at that exact instant, the monitor briefly blocks. This is why log_burnout() deliberately captures its timestamp with sim_elapsed(sim) before locking the mutex — the printed number reflects the real detection time, and only the printing (not the timestamp value) is delayed by lock contention, keeping the reported number accurate even if the actual printf executes a moment later.
The one-paragraph answer to give live in a defense "The burnout itself is deterministic — it's forced by the arithmetic of the arguments, not by luck. What can shift by a few milliseconds is only when my monitor thread notices and prints it, because usleep only guarantees a minimum sleep duration, not an exact one, and the OS scheduler doesn't promise to run my thread the instant its sleep expires. I bound that slippage in two ways: scan_coders recomputes and re-sleeps for the exact remaining time to the nearest deadline on every tick instead of polling at a fixed coarse interval, and I stamp the log timestamp before taking the print lock so lock contention delays the print, not the reported time. That keeps the observed drift well inside the sheet's own 10 ms tolerance."
